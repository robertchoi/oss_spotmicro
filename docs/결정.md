## 0-A. 🔴 공개 시뮬레이션이 잘 걷는 이유를 찾았습니다 (8/21) — 보고서 최대 재료

민호님 관찰에서 출발했습니다. *"아이작심도 파이불렛도 클로드와 같이 만든 건 제대로
못 걸었는데, **원소스의 파이불렛은 잘 걷는다**"*.

`Simulation/spotmicroai.py` 를 열어 봤습니다.

```python
# Simulation/spotmicroai.py:173~177
def changeDynamics(self, quadruped):
    for i in range(p.getNumJoints(quadruped)):
        p.changeDynamics(quadruped, i,
                         localInertiaDiagonal=[0.000001, 0.000001, 0.000001])
```

**모든 관절 링크의 회전 관성을 1e-6 으로 지웁니다.** 0.1kg·0.1m 링크의 실제 관성이
1e-4 정도이므로 100배 작습니다. 각운동량이 사실상 없어 넘어질 수가 없습니다.

| | 공개 PyBullet | 우리 MuJoCo | 실물 |
|---|---|---|---|
| 링크 회전 관성 | **1e-6 (지움)** | 실제 값 (게이트 4) | — |
| 모터 힘 | **12.5 N·m** (`spotmicroai.py:73`, 슬라이더 최대 50) | 3.0 / 2.5 N·m | DS3235 스톨 **3.43** |
| 총 질량 | **5.30 kg** (URDF 20링크 합) | **2.20 kg** (게이트 2) | **2.20 kg** |
| 기하 | URDF 186/120.4/135 ↔ IK 140/100/100 **불일치** | 0.0000mm 일치 | — |

**실제 서보의 3.6배 힘으로 관성 없는 몸을 흔드는 것**이라 어떤 궤적이든 걷습니다.

### 왜 이것이 결정적인가

지금까지 우리 서사는 "치수가 세 벌"이었는데, 그건 **정적 기하** 불일치입니다. 이건
**동역학** 불일치이고 훨씬 큽니다. 둘을 합치면 한 문장이 됩니다.

> **공개 시뮬레이션은 실물을 예측하지 못한다.** 거기서 잘 걷는다고 실물이 걷지 않고,
> 거기서 맞춘 파라미터는 넘어오지 않는다. 시뮬과 하드웨어가 따로 놀았다.

그리고 이것이 **"따라 만들면 안 걷는다"를 완전히 설명합니다.** 원작자를 탓하지도
않습니다 — 관성을 지우는 것은 초기 시각화 단계에서 흔한 선택이고, 그 위에 강화학습을
올릴 계획이 없었다면 합리적입니다.

### 우리가 반대로 한 것

| 층위 | 방법 | 결과 |
|---|---|---|
| 정적 기하 | 순기구학 대조 (게이트 3) | **0.0000 mm** |
| 기구학 | 무릎 각속도 | 323 vs 318 (**2%**) |
| **동역학** ← 신규 | 실물에서 걷는 궤적을 시뮬에 그대로 재생 (`make gait-check`) | **52 vs 49~50 mm/s (4%)** |

**동역학 층위는 오늘 처음 생겼습니다.** 게이트 3 은 기하만 증명하지 질량·관성·마찰·
서보 게인이 맞는지 말해주지 않는데, 이제 봅니다.

### 부수 결론 — 우리 RL 이 어려운 것은 정상입니다

공개 시뮬을 재현한 것이 아니라 **처음으로 정직한 문제를 푸는 중**입니다. 민호님의
Isaac Sim 이 뒹군 것도 같은 이유일 가능성이 큽니다. 다만 규칙 기반 궤적이 우리
모델에서 52mm/s 로 걷는 것이 확인됐으므로 **모델이 너무 어려운 것은 아닙니다.**

> **CTO 확인 요청**: `Simulation/` 은 상속 코드라 CTO 소유입니다. 위 인용(`:73`, `:173`)이
> 정확한지, 그리고 보고서에 이 대비를 넣을 때 표현이 과하지 않은지 봐주세요.
> COO 판단으로는 *"관성을 껐다"* 가 아니라 **"관성을 1e-6 으로 두었다"** 처럼
> 코드가 하는 일만 적는 편이 안전합니다.

### CC-17. 🔴 RL(뒷왼쪽) 다리는 하드웨어 고장입니다 — 소프트웨어로 못 고칩니다 (8/25)

민호님이 "RL-Lower 각도가 눈에 띄게 벌어졌다, 아무리 조정해도 왼쪽으로 간다" 고
보고하셨습니다. **로그가 그것을 뒷받침합니다. 수리 전에는 더 조정하지 마십시오.**

**증거 1 — 오프셋이 이미 스플라인 한 칸을 삼켰습니다.**
`RL-Lower` 가 8/19 의 164 에서 8/25 의 **176 (+12도)** 로 갔습니다. 25T 스플라인 한 칸이
14.4도, 20T 면 18도입니다. 혼이 빠지지 않은 채로 한 칸 가까이 건너뛴 값입니다.
176 은 `SAFE_BAND (8,172)` 밖이라 `servo_check.py home` 이 그 관절을 **건너뜁니다** —
기준 자세를 명령하면 서보가 자기 스토퍼를 밀며 stall 합니다.

**증거 2 — 오프셋을 다시 잡은 뒤에도 트림 13mm 가 더 필요합니다.**
촬영 세션에서 트림 조합을 **162 개** 시도했는데, `RL` 은 전부 **-5 에 고정**이었고
`RR` 만 +5 에서 +8 로 올라갔습니다. 두 뒷다리 사이 차이가 10 -> **13mm** 로 벌어졌습니다.

```
[0, 6, -5, 5]  ... [0, 0, -5, 5]  [0, 0, -5, 6]  [0, 0, -5, 7]  [0, 0, -5, 8]
                RL 은 한 번도 안 움직였고, RR 만 계속 올라갑니다
```

13mm 는 무릎에서 **약 11도**입니다 (위아래 1.2mm/도). **오프셋이 12도를 흡수한 뒤에도
11도가 더 남았다**는 뜻이고, 그것은 재캘리브레이션 이후에 관절이 **또 움직였다**는
뜻입니다. 한 번 튄 것이 아니라 **동작 중에 계속 밀리고 있습니다.**

**증거 3 — 그래서 값으로는 절대 수렴하지 않습니다.**
오프셋은 *고정된* 각도 오차를 보정합니다. 매 걸음 변하는 오차는 어떤 정적인 값으로도
못 따라갑니다. 162 개 조합이 실패한 이유가 이것입니다.

**증거 4 — 위험 구간에 들어왔습니다.**
`gait_params.py` 의 IDtrim 주석: *"차이가 Sh 에 육박하면 높은 발이 접지하지 못해
반대 대각선으로 넘어진다."* 지금 차이 13mm 에 `Sh` 는 23~28 입니다. **절반입니다.**

**왜 하필 RL 인가**: 무게중심이 뒤에 있어 뒷다리가 하중의 약 64% 를 받습니다
(work11 §6.18, 앞 800g / 뒤 1400g). 거기에 8/25 로그에서 정격 슬루 초과가
반복됐습니다 (한때 14%). 뒷무릎이 가장 먼저 갈 자리입니다.

**수리** (서보 인덱스 6, 0x41 CH13):

1. 혼 나사를 풀고 혼을 빼서 **양쪽 스플라인을 다 보십시오** — 혼 안쪽과 서보 출력축
2. **혼 쪽이 뭉개졌으면** 혼만 교체 (싸고 빠릅니다)
3. **출력축이 뭉개졌으면 서보를 교체해야 합니다** (DS3235, 약 15,000원).
   축은 기어박스와 한 몸이라 따로 못 고칩니다
4. 다시 물릴 때 **한 칸 되돌려** 오프셋이 158~162 에 오게 하십시오. 그러면
   `SAFE_BAND` 안으로 들어와 `home` 이 정상 동작합니다
5. `servo_check.py cal 6` -> 나온 값 커밋 -> **트림을 0 으로 리셋**하고 재시험

**수리 전에 오프셋·트림을 더 만지지 마십시오.** 움직이는 표적을 쫓는 것이고,
이미 162 번 시도해서 실패했습니다.

**촬영**: RL 을 쓰지 않는 그림(정면 클로즈업, 상체, 시뮬 컷)은 지금 찍을 수 있습니다.
직진 보행 컷은 수리 후가 낫습니다 — 왼쪽으로 휘는 것이 화면에 그대로 보입니다.

**우리 것은 3번(1/2 지연)이고, 그게 트롯입니다.** `positions()` 에서
FL·RR 이 위상 0, FR·RL 이 0.5 — 대각 쌍 트롯이 맞습니다.

우리 기하(Fo117.5 Ro67.5 Sp95, 무게중심 −25.2mm)에 Tt1400 / duty0.23 / 보폭 −70 을
넣고, **접지 중 발이 뒤로 흐르는 것까지 반영**해 지지다각형을 계산했습니다:

| 뒷다리 지연 | 평균 면적 | **최소 면적** | 무게중심 여유 |
|---|---:|---:|---:|
| 1. 같은 위상 | 190 | **0** (2점) | — |
| 2. 1/4 지연 | 170 | 154 | −48.6mm |
| **3. 1/2 = 트롯 (현재)** | 190 | **0** (대각선 2점) | — |
| **4. 3/4 = 크롤/워크** | **210** | **197** | **−37.5mm** |

(면적 cm², 여유는 무게중심에서 가장자리까지 · 음수면 바깥)

**영상이 "2번은 삼각형이 가늘어서 넘어진다" 고 한 것이 수치로 나옵니다** — 최소 면적이
154 대 197 로 4번이 28% 큽니다. 발을 고정 위치로 두고 계산하면 2번과 4번이 좌우 대칭이라
똑같이 나옵니다. **접지 중 발이 흐르는 것을 넣어야 차이가 생깁니다.**

**핵심은 면적이 아니라 지지 형태입니다.** 트롯은 4점 아니면 **대각선 2점(선)** 이고,
크롤은 4점 아니면 **삼각형 3점(면)** 입니다. 선 위에서는 무게중심이 조금만 벗어나도
넘어지고, IMU 가 없으니 로봇은 그걸 모릅니다. **8/25 하루를 트림으로 보낸 것이
그 선 위에 무게중심을 올리는 작업이었습니다.**

**다만 크롤로 바꾼다고 바로 서지는 않습니다.** 여유가 −37.5mm 로 여전히 음수입니다.
발 배치가 무게중심보다 앞으로 치우쳐 있어서 **뒷발을 들 때 넘어갑니다.**
약 40mm 를 메워야 하고 방법은 셋입니다:

1. 배터리·보드를 앞으로 (work11 §6.18) — 서보 여유 손실 없음. **가장 낫습니다**
2. `Fo`/`Ro` 를 뒤로 — 잘 걷는 설정이 통째로 바뀜
3. **몸통 좌우 흔들림** — 동물이 하는 것. 영상에서 개가 흔들리는 게 이것

**9월 작업 (민호님 결정)**: 트롯과 크롤 **둘 다** 구현해 고를 수 있게 합니다.

- `positions()` 의 위상을 표로 빼고 `gait` 파라미터로 선택 (`trot` / `crawl`)
- 크롤은 `duty <= 0.25` 여야 한 번에 한 발만 뜹니다. 넘으면 경고
- 흔들림은 그다음. 위상에 동기화된 몸통 좌우 이동

**보고서·RL 관점**: 흔들림의 크기와 타이밍을 손으로 맞추는 것이 8/25 트림 작업과 같은

   `duty` 를 올려 `t3` 를 두 배로 늘렸으므로 A 는 우리 기본값보다 **오히려 슬루가 낮습니다**
   (341 < 366). CC-11 이 "업스트림의 절반" 이라 지적한 `Sh` 는 이렇게 메웁니다.
2. **65% 하한은 제 착오였습니다.** 근거로 삼은 8/20 의 58% 전복은 **그때 피치 트림이 0** 이었고,
   무게중심이 대각 지지선 뒤에 있는 상태였습니다. 트림으로 무게중심을 지지선 위에 올리면
   14% 에서도 섭니다. 제가 두 변수를 하나로 묶어 보고 있었습니다.

**보고서에 쓸 수 있는 결론**: 개루프에서 네발지지를 포기할 수 있는가는 지지 비율이 아니라
**무게중심이 대각 지지선 위에 있는가**가 정합니다. 전자는 파라미터고 후자는 기구입니다.

### CC-11. 🔴 우리 보행이 업스트림보다 발을 덜 듭니다 — `Sh` 가 절반입니다 (8/25)

**work11 §6.16.2 가 `Sh=40` 을 기각한 근거가 흔들립니다.** 그 절은

r ×10  →  Tt1600  d.163  Sh30           ~410            <- 여기서 이미 달라 보임

### 8/20 세션에서 넘어진 건 — 시뮬이 예측한 방향입니다

스윙비율·주기를 탐색하다 **뒤로 몇 번 넘어졌습니다.** MJCF 검증 게이트 7 이 이미
같은 것을 가리키고 있었습니다.

```
대각 지지선   -25.0mm
무게중심      -36.4mm    <- 11.4mm 뒤
```

트롯은 주기의 일부를 대각선 두 발로만 버티고 그때 지지면은 '선'이다. 무게중심이
그 선보다 뒤에 있으면 뒤로 넘어간다. 피치 트림이 그것을 상쇄하고 있었다.

직접 방아쇠는 **스윙비율을 올린 것**으로 보입니다. `네발지지 = 1 - 2 × 스윙비율`:

| 스윙비율 | 네발지지 | |
|---:|---:|---|
| 0.143 | 71% | 기본값 |
| **0.21** | **58%** | **8/20 넘어짐** |
| 0.25 | 50% | work11 §6.16.1 주저앉음 |

**경고 임계값을 실측에 맞춰 고쳤습니다** — 50% 미만에서만 주황이던 것을
65% 미만 주황 / 55% 미만 빨강으로. 스윙비율 0.175 초과 시 경고 문구도 띄웁니다.

> **로봇은 자기가 넘어진 것을 모릅니다.** IMU 가 없어 쓰러진 채로 보행 명령을
> 계속 냅니다. 로그에도 넘어짐이 남지 않습니다. 이것이 IMU 가 강화학습 이식의
> 전제인 이유이고, 보고서 한계점에 들어갈 항목입니다.

**무릎 혼 4개 체결 확인이 이제 선택이 아닙니다.** 하루에 정격 초과 2회(최대 703°/s)에
낙하 충격까지 겹쳤습니다. work11 §6.13 에서 혼이 이탈한 전례가 있습니다.
